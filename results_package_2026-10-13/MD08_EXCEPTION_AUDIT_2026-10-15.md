# Audit of the 14 entries of `TRANSPORT_ERROR_CLASSES` (2026-10-15)

Requested by the owner on 2026-10-15 (decision record 12.42, A4). 14 entries were found in `research_design/step10/s10_resume.py` (verified by script against the table below). **Recommendations are not approvals. No class is ratified: `RATIFIED_TRANSPORT_ERROR_CLASSES` is empty and is the only set that gives eligibility.** The 14 names are audited candidates only.

## How a class gets into a record
`GeminiProvider.generate` (`s10_runner.py`, `try` around `urllib.request.urlopen` and `r.read()`) catches `urllib.error.HTTPError` (-> `http_status` set, `error = "HTTP <code>"`) and then `except Exception as e` -> `{"http_status": None, "text": "", "error": type(e).__name__}`. So every other exception, transport or not, becomes SF1 with only its class NAME stored (message, `reason`, traceback dropped). Consequences: `JSONDecodeError` (a 200 reply with a non-JSON body: observed locally) is also stored as SF1 with an empty text; the string `"no API key in the environment"` is stored as `error` too. Neither is a candidate.
`urllib` raises raw only errors from `getresponse()` and `read()`; errors while connecting or sending are wrapped into `URLError` (the wrapped `reason` is lost). The class names that can therefore appear raw are mainly TimeoutError, ConnectionResetError, RemoteDisconnected, IncompleteRead (+ TLS errors on read). Evidence: stdlib behaviour and a local-only probe (`127.0.0.1`, no provider, no external host) run 2026-10-15 under Python 3.11.9: closed port -> `URLError` (reason `TimeoutError` on this Windows host); server closes silently -> `RemoteDisconnected`; RST after request -> `ConnectionResetError`; truncated body -> `IncompleteRead`; non-JSON 200 -> `JSONDecodeError`; silent server -> `TimeoutError`. Not probed: DNS (`gaierror`, would need the network), TLS classes, BrokenPipe, ConnectionAborted, ConnectionRefused as a raw name.
A failed call is never re-run by a resume (spec 13.8), so "duplicate execution" is not a resume risk; the risks are (a) resuming over a standing non-transport fault and (b) unrecorded provider-side processing and billing (covered by the conservative cost bound that counts unknown usage at the worst case).

## Evidence that would resolve NEEDS_EVIDENCE (a code change, not made here)
Store the class of `URLError.reason` (and `__cause__`) in the raw record, so that a connect-phase TLS or DNS fault can be told from a transient loss. That changes the stored record format and the request/response layer, so it belongs to a pure-implementation-fix assessment (H1-H4) or to the code freeze decision, and needs an owner decision.
